## 2. Alvo `make ci`

Objetivo: reproduzir na máquina, com um comando, os dois jobs de
`.github/workflows/ci.yml`. Hoje isso é feito à mão (status do B04f).

```make
ci: ci-test ci-prod
	docker image prune -f
```

- **Contexto limpo:** a imagem é construída a partir dos arquivos do índice
  do Git (`git ls-files` empacotado com tar e enviado ao `docker build -`),
  não da árvore de trabalho. Assim o build vê o mesmo que o checkout do CI:
  arquivo novo sem `git add` fica de fora, como no CI (D8).
- **ci-test:** `--target dev`, com a tag `maprelations-app`. Roda os seis
  passos do job `test`, na mesma ordem, com `docker run --rm` **sem volumes
  e sem `user: "0:0"`**, isto é, com o código assado na imagem e o
  `appuser`, como no CI: ruff, mypy, `generate_schemas --check`,
  `ontology check`, `generate_ontology --check` e pytest.
- **ci-prod:** `--target prod`, com a tag `map-relations-prod`, e os dois
  testes de fumaça do job `build-prod`.
- **Sincronia:** um teste lê o `ci.yml` e o Makefile e falha se a lista de
  comandos `docker run` do job `test` divergir da lista do alvo `ci-test`.
  A cópia manual não tem como divergir em silêncio.
- **Princípio 14:** acrescentar que `make ci` também constrói
  `map-relations-prod` localmente e faz o prune ao final.
- `make check` continua sendo o ciclo rápido, com volumes. `make ci` é o
  portão antes do commit de fechamento e do PR.

## 3. Formato do gabarito

Modelo Pydantic `GoldFile` em `research/map_relations/evaluation/gold.py`,
com JSON Schema gerado em `contracts/schemas/gold.schema.json` (entra no
`generate_schemas --check`). O arquivo começa com exemplos marcados como
fictícios (`"fictional": true`), que o avaliador ignora.

```json
{
  "schema_version": 1,
  "work": "<título>",
  "source": { "content_hash": "sha256:…", "offset_unit": "codepoint_nfc", "end": "exclusive" },
  "ontology_version": 1,
  "scope": { "chapters": ["1", "2", "3"], "narrative_scopes_evaluated": ["obra"] },
  "annotation_rules": ["…texto livre…"],
  "entities": [
    { "id": "ana_exemplo", "preferredName": "Ana Exemplo", "aliases": ["Ana", "a vizinha"], "fictional": true }
  ],
  "relations": [
    {
      "id": "r_<claim_key curto>",
      "subject": "ana_exemplo",
      "type": "exerce_vigilancia_sobre",
      "object": "bruno_exemplo",
      "class": "alegada",
      "asserted_by": "carla_exemplo",
      "narrative_scope": "obra",
      "origin": "modelo_revisado",
      "origin_detail": { "model": "…", "reviewed_by": "humano", "note": "…" },
      "evidence": [
        {
          "chapter": "1",
          "anchor": { "exact": "…", "prefix": "…", "suffix": "…", "startOffset": 0, "endOffset": 0 },
          "support": "alto",
          "polarity": "apoia",
          "note": "opcional"
        }
      ],
      "provas_em_conjunto": "suficiente",
      "fictional": true
    }
  ],
  "negative_pairs": [
    { "subject": "ana_exemplo", "object": "carla_exemplo", "chapters": ["1"], "expected": "sem_relacao", "fictional": true }
  ]
}
```

Validação feita por código (`gold validate`, também chamada pelo `eval`):

- `type` existe, está ativo e não é abstrato. A visão inversa é aceita e
  normalizada por `Ontology.canonicalize` na leitura.
- `class` ∈ contrato; `asserted_by` presente se e somente se
  `class = alegada`, e aponta para uma entidade do arquivo.
- `narrative_scope` ∈ {`obra`, `texto_encaixado`}; o campo é obrigatório no
  gabarito (sem ausência implícita, para o anotador decidir sempre).
- `origin` ∈ {`modelo`, `humano`, `modelo_revisado`}. `origin_detail.model`
  é obrigatório para `modelo` e `modelo_revisado`.
- Sem relação reflexiva em tipo irreflexivo; disjunções entram como alerta,
  sem rejeição (reuso de `disjoint_conflicts`).
- Nenhuma duplicata de `claim_key` (simetria lida do tipo). `id` é derivado
  da chave, o que dá estabilidade entre versões do arquivo.
- Toda âncora confere com o canônico do `content_hash` (§4); hash diferente
  do canônico atual é erro, com a mensagem "rode fill-offsets".
- `chapter` é gravado na evidência (decisão de anotação, revisão de 2026-11-24) e
  conferido contra `locate(startOffset)`; divergência é erro.
- Prova: provada se há evidência `alto` que `apoia` ou `provas_em_conjunto:
  suficiente`. Alerta se declarada suficiente com soma de pesos (alto=3, medio=2,
  baixo=1) abaixo do corte (4); pesos e corte provisórios, a calibrar no B03
  (ADR 012). Nada calculado é gravado no gabarito.
- `negative_pairs` não pode coincidir com nenhum par de `relations` dentro
  dos mesmos capítulos.

## 4. Âncora de evidência (estilo W3C TextQuoteSelector)

Cada evidência combina um TextQuoteSelector (`exact`, `prefix`, `suffix`)
com um TextPositionSelector (`startOffset`, `endOffset`) sobre o canônico NFC,
em code points, com fim exclusivo (ADR 004).

- **Invariante:** `text[start:end] == exact`, com `prefix` imediatamente
  antes e `suffix` imediatamente depois (cortados na borda do texto).
- **Tamanho do contexto:** 32 code points de cada lado por padrão (D7),
  ajustados para não cortar palavra ao meio. A âncora é **mínima
  suficiente**: o contexto gravado precisa deixar a citação única no
  canônico; se 32 não bastarem, o fill-offsets aumenta até 128 e, se ainda
  assim houver ambiguidade, reporta erro.
- **Papéis:** a posição é o atalho rápido e a citação com o contexto é a
  verdade. Quando divergem, vale a citação, e o fill-offsets reconstrói a
  posição.
- **Relação com o domínio:** `Evidence` (quote e offsets) não muda neste
  bloco. Levar `prefix`/`suffix` ao modelo de domínio é entrada do B05
  (§10).
- **ADR 012** registra o formato da âncora e a regra "nunca chute".

## 5. `fill-offsets`

Comando: `python -m map_relations gold fill-offsets --gold <arq> --canonical <canonical.txt> --out <arq>`
(alvo `make gold-fill GOLD=… OUT=…`). O `--canonical` pode ser omitido se
houver uma única pasta em `data/processed/` com o documento; nunca há
caminho padrão para `data/golden/`.

Algoritmo, por âncora:

1. Busca todas as ocorrências de `exact` no canônico atual.
2. Se houver exatamente 1, aceita. Se `prefix` ou `suffix` mudaram em volta
   dela, o contexto é regravado e entra no relatório como **aviso**
   ("contexto atualizado"), não como erro (D3).
3. Se houver mais de 1, filtra pelas ocorrências cujo contexto bate com
   `prefix` e `suffix` gravados. Se restar exatamente 1, aceita. Se restarem
   0 ou mais de 1, gera erro `ambigua`, com a lista de candidatas em
   `locate()` ("cap. X, § Y").
4. Se houver 0, gera erro `nao_encontrada`.
5. **Nunca** usa o offset antigo, a distância ao offset antigo, um ordinal
   nem casamento aproximado para escolher. O offset antigo só aparece no
   relatório, como informação.

Saída:

- Tudo ou nada: com qualquer erro, nada é gravado, a lista de erros vai
  para a saída e o código de saída é 1. Sem erro, grava `--out` com as
  posições e os contextos novos e `source.content_hash` atualizado.
- `--out` nunca pode ser igual a `--gold` (o rascunho e as versões
  anteriores ficam intactos, porque `data/golden/` não tem histórico no Git).
- O relatório (JSON e uma tabela legível) lista, por relação: aceitas sem
  mudança, aceitas com posição nova, contexto atualizado e erros.
- **Modo âncora mínima:** uma evidência com só `exact` (sem contexto nem
  posição) é aceita como entrada. É assim que o Leon anota o capítulo de
  controle (§9): copia a citação e o comando preenche o resto.

## 6. Conversão do rascunho

Comando de uso único, `python -m map_relations gold convert-draft --draft
data/golden/processo.json --canonical … --out data/golden/processo.gold.json`.
A lógica fica em `evaluation/convert_draft.py`, com testes sobre um rascunho
sintético no mesmo formato. O arquivo real nunca é lido inteiro na conversa:
o comando só imprime contagens e erros.

Passos:

1. **Entidades:** `id` = slug de `preferredName` (casefold, sem acentos,
   `_`). Colisão de slug é erro. `aliases` são mantidos.
2. **Nomes → ids** em `subject`, `object`, `asserted_by` e `negative_pairs`,
   por casamento exato com `preferredName`/`aliases`. Zero ou mais de um
   casamento é erro.
3. **Tipos:** tabela fixa `{"vigia": "exerce_vigilancia_sobre"}`; depois
   `Ontology.canonicalize` e validação de tipo ativo e anotável.
4. **Classe e asserted_by:** mantidos; a regra "se e somente se" é
   validada.
5. **`narrative_scope = "obra"`** em todas, listadas no relatório para o
   Leon confirmar (A3).
6. **`origin = "modelo"`**, com `origin_detail.model` vindo do rascunho
   quando houver, ou `"desconhecido"`, para não inventar.
7. **Evidência:** `quote` vira `exact`. Os offsets antigos são descartados
   (A1) e a âncora é preenchida pela mesma rotina do §5. O caso ambíguo (A2)
   sai como erro, com as duas candidatas localizadas e a indicação de que o
   rascunho usava a 1ª ocorrência. O relatório mostra **só** as duas
   candidatas, cada uma com o seu contexto imediato e `locate()`, nunca o
   capítulo nem o parágrafo inteiro. O Leon escolhe olhando só esse trecho,
   acrescenta um `prefix` à mão e roda o comando de novo (D4).
8. **Capítulo:** o `chapter` do rascunho é comparado com `locate()` da
   posição nova; divergência é erro.
9. **`negative_pairs`:** `"capítulos 1-3"` vira `["1","2","3"]` e o
   resultado esperado vira `"sem_relacao"`.
10. **Cabeçalho:** `ontology_version` inteiro, `annotation_rules` copiadas
    (incluindo a regra do cabeçalho e rodapé do digitalizador, cuja validade
    no canônico atual é conferida pelo Leon) e `occurrences_in_text`/
    `occurrence_used` removidos.

O rascunho fica intocado. `processo.gold.json` é o gabarito do B02 (D2).

## 7. Avaliação

Pacote `research/map_relations/evaluation/` (o nome evita sombrear o
builtin `eval`). Comando: `python -m map_relations eval --run <arq> --gold <arq> [--canonical …] [--track]`
(alvo `make eval RUN=… GOLD=…`), sem padrão apontando para `data/golden/`.

**Formato de execução** (`RunFile`, com schema gerado): metadados
(princípio 10: modelo, versão do prompt, parâmetros, nível e lente), as
entidades propostas com nomes e as claims com tipo, classe, `asserted_by`,
`narrative_scope`, evidências (quote e offsets) e, por chamada,
`json_valid`. O B03 passa a emitir esse formato. No B02 ele só existe em
fixtures sintéticas (`eval/gold/` e `tests/fixtures/`).

**Alinhamento:**

1. Cada entidade da execução é ligada a uma entidade do gabarito por nome
   ou alias normalizado (NFC, casefold, sem acentos). Alias que casa com
   duas entidades do gabarito é erro de gabarito. Entidade sem casamento
   fica "não alinhada".
2. Tipo inverso normalizado por `canonicalize`. Duas chaves de casamento
   (D5):
   - **estrita:** `claim_key` do ADR 011 (simetria do tipo, `asserted_by` e
     `narrative_scope` na chave, classe fora);
   - **relaxada:** a mesma chave sem `asserted_by` (a classe já fica fora),
     isto é, sujeito, tipo, objeto e `narrative_scope`.
3. **Filtro de escopo:** só entram claims com evidência nos capítulos do
   gabarito. As outras são contadas como "fora do escopo", sem afetar a
   precisão.

**Casamento, com cada item do gabarito usado no máximo uma vez.** As duas
medidas são calculadas de forma independente e ambas vão para o relatório:

- **Acerto exato:** mesma chave (estrita ou relaxada, conforme a medida).
- **Acerto no tipo pai:** mesmo par, tipo diferente, mesmo
  `ancestors()[0]`. A direção é exigida quando os dois tipos são
  assimétricos e ignorada quando um deles é simétrico. Feito depois do
  exato, sobre o que sobrou.
- **Leitura conjunta:** a relaxada mede "achou a relação"; a diferença
  entre as duas mede "atribuiu certo quem afirma". Nos acertos relaxados,
  o relatório traz a taxa de atribuição correta: classe igual e, quando o
  gabarito diz `alegada`, o mesmo `asserted_by`.

**Métricas (relatório JSON e Markdown):**

| Grupo | Conteúdo |
|---|---|
| Por tipo | P, R e F1 exatos, micro e macro, nas medidas estrita e relaxada |
| Por família | P, R e F1 com acerto no tipo pai, nas duas medidas (cobre o ponto aberto `age_em_nome_de` × `representa_juridicamente`) |
| Atribuição | nos acertos relaxados: % com classe certa, % de alegadas com `asserted_by` certo, lista das atribuições erradas |
| Classe | matriz de confusão classe do gabarito × classe da execução nos acertos relaxados |
| Nível e lente | P, R e F1 por `level` e `lens` dos metadados |
| Provas | % de evidências localizadas (`canonical[start:end] == quote`, princípio 4); % que se sobrepõem a uma evidência do gabarito do mesmo par |
| JSON válido | % de chamadas com `json_valid` |
| Pessoas | recall de entidades do gabarito alinhadas; lista das não alinhadas dos dois lados |
| Pares de controle | violações: qualquer claim, de qualquer tipo e direção, num par de `negative_pairs` dentro dos capítulos dele; taxa e lista |
| Texto encaixado | à parte: no gabarito e na execução, quantos `texto_encaixado` e acertos entre eles. Saem das métricas principais nos dois lados. Uma claim da execução marcada `obra` que casa com um item `texto_encaixado` do gabarito conta como falso positivo (ADR 011) |
| Alertas | disjunções na execução (`disjoint_conflicts`) |

O relatório vai para `eval/reports/<run_id>/` (`report.json` e
`report.md`). Ele cita trechos da obra, então `.gitignore` passa a ignorar
`eval/reports/*`, com exceção de `.gitkeep`. O código de saída é 0 com
relatório gerado e 2 com gabarito ou execução inválidos.

## 8. MLflow

- **Serviço** `mlflow` no `docker-compose.yml`, perfil `mlflow`, imagem
  oficial `ghcr.io/mlflow/mlflow` com versão exata fixada na implementação.
  O comando é `mlflow server` com backend SQLite e artefatos em
  `/mlflow`, publicado só em `127.0.0.1:5010` (D6). O alvo `make mlflow`
  sobe o serviço.
- **Dados** em `./mlflow_data/` (montado em `/mlflow`), listado no
  `.gitignore` e no `.dockerignore`. Nada vai para o Git nem para a
  imagem.
- **Contrato (princípio 2):** Protocol `RunTracker` em `core/protocols.py`
  (`start`, `log_params`, `log_metrics`, `log_artifact`, `set_tags`,
  `end`). Adaptadores: `MlflowTracker`, em `research/map_relations/tracking/`
  (usa `mlflow-skinny` no grupo dev, com import local), e `NullTracker`, o
  padrão. `eval --track` usa `MLFLOW_TRACKING_URI` do `.env`.
- **Proteção (princípio 6):** o adaptador recusa URI cujo host não seja
  `mlflow`, `localhost` ou `127.0.0.1`. Os trechos protegidos só existem no
  artefato do relatório, nunca em parâmetros ou tags.
- **O que registrar:** parâmetros (hash do gabarito, hash do canônico,
  `ontology_version`, modelo, versão do prompt, parâmetros, nível e lente),
  todas as métricas do §7 como números com nomes estáveis
  (`p.estrita.<tipo>`, `p.relaxada.<tipo>`, `f1.familia.relaxada.<pai>`,
  `atribuicao.asserted_by`, `controle.violacoes`…) e o
  relatório como artefato.
- **CI:** sem servidor. Os testes usam `NullTracker` e um teste do
  adaptador grava em `file://` num diretório temporário.
- **B02b reduzido:** tabelas de métricas, histórico e comparação entre
  execuções passam a ser do MLflow. O B02b fica só com as telas de domínio:
  (1) leitor da execução com as evidências destacadas no texto e
  `locate()`; (2) execução × gabarito por par (acerto exato, pai, falso
  positivo, falso negativo); (3) pares de controle violados;
  (4) texto encaixado; (5) revisão gravada em `eval/reviews/<run_id>.jsonl`,
  a única escrita. A seção B02b do CLAUDE.md é reescrita nessa linha na
  conclusão do B02, com a sua aprovação.

## 9. Capítulo de controle anotado pelo Leon

- **Capítulo (D9):** cap. 5, o do açoitador. É curto e concentra relações
  de poder, coerção e uma alegação falsa: exercita `relacao_de_poder`, a
  classe `alegada` e as duas medidas do §7 (estrita × relaxada) num trecho
  pequeno.
- **Consequência:** o gabarito do modelo cobre só os caps. 1–3, então hoje
  não há com o que comparar no cap. 5. O modelo precisa anotar o cap. 5 no
  mesmo formato (`origin = modelo`, mesmas regras, mesmas entidades), **sem
  ver a anotação do Leon**, num arquivo separado,
  `data/golden/processo.modelo.cap5.json`. Depois da adjudicação, o cap. 5
  entra em `processo.gold.json` e `scope.chapters` passa a `["1","2","3","5"]`.
  Pendência: decidir quem gera essa anotação do modelo (o mesmo processo
  externo que produziu o rascunho, ou uma sessão dedicada) antes da fase 6.
- **Às cegas:** `gold template --gold processo.gold.json --chapter 5 --out
  data/golden/processo.controle.cap5.json` gera um arquivo com cabeçalho,
  entidades e regras, **sem relações nem pares de controle**. Entidades
  novas do cap. 5 são acrescentadas pelo Leon com o mesmo padrão de id
  (D1). Ele anota relações e pares de controle com `origin = humano` e
  evidência só com `exact`, e o fill-offsets completa.
- **Comparação:** `gold compare --reference processo.controle.cap5.json
  --candidate processo.modelo.cap5.json --chapter 5` usa o mesmo motor do
  §7, com o humano como referência: P, R e F1 estritos e relaxados, por tipo
  e por família, taxa de atribuição, matriz de classe e lista de
  divergências com `locate()`. A alegação falsa é conferida
  nominalmente: classe `alegada` com o `asserted_by` certo nos dois lados.
  O resultado vai para `docs/blocks/B02.md` só em números, sem trechos.
- **Adjudicação** (decisão do Leon, item a item): a relação do modelo
  confirmada vira `modelo_revisado`; a recusada sai; a que só o Leon anotou
  entra como `humano`. A taxa de concordância decide se os caps. 1–3 do
  modelo precisam de revisão completa ou por amostra, e essa decisão fica
  registrada no relatório do bloco.

  casos; o que sobrar vira erro, nunca chute.
